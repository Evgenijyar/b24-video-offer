Update 024 — video pipeline stabilization, real progress and recorder UX
Date: 2026-08-10
Base: Update 023

MOBILE
- Added a short start-recording audio cue. AudioContext is primed from the user gesture; the cue finishes immediately before MediaRecorder starts so it is not intentionally recorded into the video.
- Fixed replacement/upload races: stale create-session/chunk requests can no longer overwrite or mutate the active upload after the user chooses another file/source.
- Old XHR chunk uploads are aborted when a file/recording is replaced; stale retries are cancelled by upload generation.
- Async normalization now tolerates the upload being deleted/replaced while FFmpeg is running; this is treated as normal cancellation rather than NoSuchElementException.
- Selected-file card remains visible after selection; the large Choose video control stays hidden; Replace reopens the file picker and can safely replace the file.
- Recorded camera preview is reattached robustly; normalized recording uses native video controls and preload=auto; first frame is prepared for immediate preview.
- Unified user-visible progress wording to “Загрузка видео”. Removed separate queue/saving/preparing/public-page wording from Bitrix mobile flow.
- Unified mobile progress is based on real network byte progress (0..65) plus real server media-processing progress (66..99), READY=100.

DESKTOP RECORDING
- Removed all popup/helper-window screen-capture behavior. There is no screen-recorder helper endpoint/window in this build.
- Selecting Screen immediately calls navigator.mediaDevices.getDisplayMedia() from the in-app user gesture; no separate “Choose window” button is required.
- Screen capture request uses minimal initial constraints, then applies max 1280x720 / 30 fps after the user has selected a surface.
- Added precise in-app error classification for InvalidStateError, NotAllowedError/PermissionDeniedError and NotReadableError.
- Added desktop client diagnostics endpoint/events: CAPABILITIES, SCREEN_CAPTURE_REQUEST/READY/ERROR, CAMERA_READY and recording-start events. This makes Bitrix host/permission failures visible in server logs.
- Fixed frozen live camera preview at recording start: clearRecordedPreview no longer pauses a live srcObject.
- Desktop recorder bitrate increased to 3.5 Mbps video / 128 kbps audio; camera contentHint=motion, screen contentHint=detail.
- Recorded video now uses the same native controls model as uploaded-file preview.
- Added fullscreen controls for uploaded and recorded preview. Native Fullscreen API is tried first; if the Bitrix iframe rejects it, an iframe-local fullscreen fallback fills the available application area.
- Screen and camera source switching remains in one recording session. Screen is constrained to 1280x720 to improve the probability that segment merge can use stream copy.

FILE UPLOAD / MEDIA PIPELINE
- MP4 + H.264 + AAC is accepted after ffprobe with no FFmpeg, no transcode semaphore and no copy.
- H.264 in a different container is remuxed with video stream copy. If audio is already AAC it is copied too; otherwise only audio is converted.
- Full H.264 re-encode is now a fallback only for genuinely incompatible video codecs (for example HEVC/VP8/VP9).
- Full fallback transcode changed to libx264 ultrafast / CRF 20 / automatic threads. Removed forced 30 fps conversion from normalization.
- Segment-merge fallback also uses ultrafast / CRF 20 and no forced fps=30 filter.
- FFmpeg full-transcode progress is parsed from -progress pipe:1 and persisted as actual media-time progress.
- Both desktop and mobile file/recording uploaders show real byte-level XHR progress from the first bytes sent.
- Desktop in-progress file replacement is now cancellable and generation-safe; selecting the same file again is also supported.

YOUTUBE / EXTERNAL URL
- yt-dlp now prefers MP4 H.264/AVC + M4A/AAC up to 1080p before codec fallbacks, minimizing the need for a second full video encode.
- yt-dlp download percent is parsed from its real progress output. Unified link progress reserves 0..60 for download and 61..99 for actual normalization if fallback processing is required.
- If the downloaded result is already compatible MP4/H.264/AAC, it is atomically moved into final video storage instead of being transcoded or accidentally deleted.
- The previous long 92% stall is removed: fallback FFmpeg progress now continues through the same progress bar.

DATABASE / BUG FIXES
- Added Flyway V6__video_pipeline_progress_and_quality.sql.
- video_offer.video_quality widened from VARCHAR(30) to VARCHAR(120), fixing PostgreSQL “value too long for type character varying(30)” for quality strings such as external-mobile-h264-normalized.
- mobile_video_upload.processing_progress_percent added for real async processing progress.
- MobileVideoUploadProcessor no longer uses Optional.orElseThrow after an asynchronous transcode when the user may have replaced/deleted that upload.

FINAL OFFER UX
- Removed public preview/open-preview controls from Bitrix mobile and desktop ready state.
- Ready state is limited to “Видеооффер готов” + timeline delivery/view-notification message.
- Removed stale “task queued”, “saving”, “preparing”, “public page ready” user-facing stages from Bitrix mobile/desktop flows.

VALIDATION PERFORMED IN DEVELOPMENT ENVIRONMENT
- node --check: all active static JavaScript files pass.
- Desktop/mobile JavaScript element-ID consistency checked against HTML: no missing referenced IDs.
- Changed media/backend Java classes were syntax-checked with javac 21 using strict dependency stubs.
- Real FFmpeg smoke tests passed for:
  * compatible MP4/H.264/AAC fast path (no transcode),
  * H.264 MOV -> MP4 remux,
  * incompatible codec -> H.264 full fallback with progress callback.
- Full Maven build was not available in the model container because Maven/dependency network access was unavailable; production deployment should still run the normal Docker/Maven build as the final integration gate.
